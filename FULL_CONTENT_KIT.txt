--- 🟦 LINKEDIN (Architect Perspective) ---
Stop pretending stateless JWTs are a silver bullet for auth. In a real-world e-commerce API, "pure" statelessness is just a security vulnerability waiting to happen.

**The Problem: The Illusion of Control**
If you issue a 1-hour access token and a user’s laptop is stolen, you’re toast. Without a server-side session check or a revocation list, that thief has a 60-minute all-access pass to your checkout flow. You can't "log out" a stateless token.

**The Solution: Hybrid Session Management**
In `auth.service.ts`, we’re moving away from "simple" auth toward a stateful refresh/stateless access pattern.

*   **Refresh Token Rotation:** Every time a new access token is requested, the old refresh token is invalidated. This detects replay attacks immediately.
*   **Custom Exception Hierarchy:** We use `TokenBlacklistedException` and `InvalidTokenException` instead of generic 401s. This isn't for UX; it’s for observability and preventing side-channel leaks.
*   **Database-Backed Sessions:** We use Prisma to track `randomUUID` session IDs. This allows us to kill a user's entire session fleet if we detect suspicious activity.
*   **Bcrypt & Class-Transformer:** Hashing is non-negotiable, and we use `plainToInstance` to ensure we don't accidentally leak password hashes in the JSON response—a classic junior mistake.

**Trade-offs & Reality Check**
*   **Latency:** Every token refresh now requires a DB hit. You’re trading a few milliseconds of performance for the ability to actually secure your data.
*   **Storage Bloat:** You’re now storing session metadata. If you don't implement a TTL cleanup job, your Prisma-managed DB will eventually crawl under the weight of expired UUIDs.
*   **Complexity:** This is significantly harder to debug than a simple `jwt.sign()` call.

**What happens if you skip this?**
If you go the "easy" route, you lose the ability to force-logout users after a password reset. You’ll have orphaned sessions with high-privilege access roaming your system. In a production environment, that's not a bug; it's negligence.

**The Question:**
If your "stateless" JWT implementation doesn't have a mechanism to invalidate a specific token before it expires, are you actually managing security, or just hoping for the best?

FILE: user-service\src\modules\redis\redis.service.ts | SIGNALS: ['retry', 'timeout']
============================================================

--- 🟦 LINKEDIN (Architect Perspective) ---
Most developers treat Redis as an "always-on" utility like electricity. It’s not. If your application logic assumes a 100% uptime for your cache, your "scalable" E-commerce API is just a house of cards waiting for a network blip to collapse.

### The Problem: Cascading Failures
When Redis hangs or restarts, a naive client implementation will either block the event loop, throw unhandled exceptions, or—worst of all—retry infinitely with no delay. This creates a "retry storm" that ensures your cache stays dead even after the service recovers.

### The Solution: Linear Backoff with a Ceiling
In `user-service\src\modules\redis\redis.service.ts`, we use `ioredis` with a custom `retryStrategy`. We don’t just "try again."

```typescript
retryStrategy: (times) => {
  // Linear backoff: 50ms, 100ms, 150ms... 
  // Capped at 2 seconds to avoid permanent latency.
  const delay = Math.min(times * 50, 2000);
  return delay;
}
```

By capping the delay, we ensure the service remains responsive. We’re prioritizing a fast failure over a slow, agonizing hang that consumes all available connections in your pool.

### Trade-offs & Reality Check
*   **Memory Pressure:** While retrying, the client buffers commands in memory. If your Redis is down for 10 minutes and you have high traffic, you’ll hit an OOM (Out of Memory) error on your Node.js process before Redis ever comes back.
*   **Stale Data:** A retry strategy keeps the app alive, but it doesn't solve the "cache miss" problem. Your database is about to get hammered by every request that used to be cached.
*   **Complexity:** Managing `isConnected` state manually is prone to race conditions if not handled within the `onModuleInit` lifecycle correctly.

If you don't implement a sane retry and timeout policy, a 30-second network hiccup in your VPC will trigger a total system outage. You’ll be debugging "Socket Hang Up" errors while your database CPU hits 100%.

**For the Seniors:** At what point do you stop retrying and flip a circuit breaker to bypass the cache entirely, and how do you prevent the "thundering herd" when that breaker finally resets?
